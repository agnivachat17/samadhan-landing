# USP-08 — Intelligent Problem-to-Institution Matching & Routing Engine

**Status: Implemented.** Everything below the "Implementation (as shipped)" section is the *original design spec*, kept as-is for historical context — it's still an accurate description of the problem and the reasoning, just not of the current code (e.g. it proposes a keyword-only scorer as the whole solution; the shipped version uses that only as a fallback, see below). If the two ever disagree, the implementation section is authoritative. Also see `CLAUDE.md`'s own "USP-08" section, which covers the same ground in the context of the rest of the app.

## Implementation (as shipped)

This section is written to be understood on its own, without reading the app's source code or `CLAUDE.md` first. It explains exactly what exists, in which files, how the pieces connect, and how it behaves in every state (success, loading, error, no-data).

### The one-sentence version

Samadhan asks Groq's `qwen/qwen3.6-27b` model to score how well each open citizen-reported problem fits a given institution's academic profile (or vice versa), and shows that score with the model's own plain-English reasoning; if that call is unavailable for any reason, a small deterministic keyword-and-location scorer instantly fills in instead, clearly labeled as an "offline estimate" rather than AI.

### Why two scorers exist, not one

The first cut of this feature was keyword-overlap-only — no model call at all. That was corrected after review: the SIH problem statement explicitly asks for an "AI-enabled problem management module" that routes challenges, and a hand-written scoring formula, however well-tuned, is not what that requirement means. The AI call (Groq) is now the *primary* mechanism everywhere in the product. The keyword scorer was **not deleted** — it was kept and demoted to an *offline fallback only*, used in exactly two situations: (a) for the first render, before the AI response has come back, so the page is never blank or stuck on a spinner with nothing else to show; (b) if the AI call fails outright (no API key configured, a network error, or Groq's rate limit — this was verified with a real `429` during testing, see "How this was verified" below). **The UI always tells the user which one it's looking at** — an AI-sourced score gets a `BrainCircuit` icon and "AI-powered"/"AI-ranked" copy; a fallback score gets a `Target` icon and "Offline estimate" copy. A fallback score is never presented as if it came from AI.

### File-by-file map

- **`client/src/lib/groqClient.ts`** — the shared low-level Groq client. One exported function, `callGroqJSON(messages, options)`, which: reads the API key from `import.meta.env.VITE_GROQ_API_KEY` (the same key Samadhan's pre-existing image-auto-categorize feature uses — see `docs/update1.md` / `CLAUDE.md`'s "AI Auto-Categorize" section; this is a `VITE_`-prefixed env var, so it is bundled into the client JS and visible to anyone who opens devtools — an accepted tradeoff for a hackathon build with no backend, documented elsewhere, not new here); POSTs to `https://api.groq.com/openai/v1/chat/completions` with model `qwen/qwen3.6-27b`; and parses the model's text response into a JS value via `extractJson()`, which strips `<think>...</think>` blocks (this model emits internal reasoning there even when told not to), tries `JSON.parse` directly, and falls back to regex-extracting the first top-level `{...}` or `[...]` span if the model wrapped the JSON in prose or markdown fences despite instructions not to. This file did not exist before this change — it was pulled out of `groqVision.ts` (the pre-existing image-analysis file) once there were two real call sites that both needed the same fetch/parse logic, so `groqVision.ts` now calls `callGroqJSON` too instead of duplicating it.
- **`client/src/lib/aiMatching.ts`** — the actual routing logic, two exported functions:
  - `rankChallengesForInstitution(institution, challenges)` — given one institution's profile and a list of open challenges, returns `Promise<Map<challengeId, { score, reasons }>>`. Used by the institute-facing pages (which show "which challenges fit me").
  - `rankInstitutionsForChallenge(challenge, institutions)` — the mirror image: given one challenge and a list of verified institutions, returns `Promise<Map<organizationId, { score, reasons }>>`. Used by the admin page (which shows "which institutions fit this challenge").
  - Both functions make **exactly one** Groq API call per invocation, no matter how many challenges/institutions are in the list (capped defensively at 60 challenges / 40 institutions per call via `MAX_CHALLENGES_PER_CALL` / `MAX_INSTITUTIONS_PER_CALL` — not reached by the current live dataset of ~50-something challenges and a handful of institutions, just a safety ceiling).
  - **Why short refs instead of real ids:** Firestore document ids in this app are large synthetic numbers (e.g. `1787634066252602`). Early testing showed the model would occasionally mistype or truncate these when echoing them back in its JSON response. To avoid that entirely, the prompt assigns each challenge/institution a short label — `C1`, `C2`, `C3`, … or `I1`, `I2`, `I3`, … — in the order they're sent, asks the model to key its response by that label, and the function maps the label back to the real numeric id locally afterward (`refToId` map). The model never has to get a 16-digit number right.
  - **The system prompt** (`ROUTING_CONTEXT` constant, shared by both functions) explicitly quotes the SIH problem statement's own language back to the model — "routing validated problem statements to appropriate universities based on their academic disciplines, research expertise, innovation centres, incubation facilities, and faculty specialization" — and then adds an explicit anti-inflation instruction: *"two things merely being in the same state (Jharkhand) is NOT a reason to score highly on its own — a genuine match must relate to the institution's actual stated departments, expertise, or priority domains. Never inflate a score just to be encouraging; a poor match should score low."* This sentence exists because the earlier keyword-only fallback scorer had exactly this failure mode before it was fixed (see the fallback section below) — the same risk was flagged directly to the model instead of only being handled in code.
  - Each function's user-facing prompt payload is a single JSON object: the subject (one institution or one challenge, with its real fields — `departments`, `expertise`, `priorityDomains`, `location` for an institution; `domain`, `district`, `title`, `description` for a challenge, with `title`/`description` truncated to keep the payload small) plus the list of the other side (each entry tagged with its `ref`). The model is instructed to return **only** a raw JSON array, one entry per ref, each `{ "ref": "...", "score": 0-100, "reasons": ["...", ...] }`, with every ref included exactly once. `temperature: 0.2` (low, for consistency between re-runs) and a generous `max_tokens` (4096 for the challenges call, 3072 for the institutions call, since a 50-challenge response with 1-2 reasons each is a few thousand tokens).
  - Response parsing (`parseScoredArray`): anything that isn't a well-formed array, or an entry whose `ref` doesn't match a known id, is silently skipped rather than thrown — a partially-malformed AI response still produces whatever valid entries it contains rather than failing the whole call. Scores are clamped to `[0, 100]` and rounded; `reasons` is capped to the first 3 entries and coerced to strings, defensively, in case the model returns something unexpected there.
- **`client/src/lib/matching.ts`** — the deterministic offline-fallback scorer, `scoreInstitutionsForChallenge(challenge, organizations, assignments): MatchResult[]`. Pure function, no network/Firestore calls, computes instantly. Only scores organizations where `kind === "institution" && verificationStatus === "verified"`. Four signals combine into a 0-100 score:
  1. **Keyword overlap** (up to 55 points) — the challenge's `domain` + `description` and the institution's `departments` + `expertise` + `priorityDomains` are each tokenized (lowercased, split on non-alphanumerics, words ≤3 characters and a short stopword list dropped) into word sets, and the size of the intersection determines this score (`15 + overlap.length * 20`, capped at 55 — so even a single shared word crosses 35, the "good fit" badge threshold, on its own).
  2. **Geographic proximity** (up to 25 points) — both the challenge's `district` and the institution's free-text `location` field are resolved to a lat/lng centroid via `findDistrictCentroid()` (`client/src/lib/jharkhandDistricts.ts`, a small fuzzy-substring-match lookup against Jharkhand's 24 districts, reused unchanged from the existing GIS/map features — nothing new was built for this), then compared by haversine distance and bucketed into "near" (<40km) / "reasonably close" (<150km) / "same general area" (<300km) tiers.
  3. **Current active caseload** (up to 15 points) — counts how many `pending`/`accepted` assignments the institution already has (from the `assignments` collection passed in), and reduces the contribution as that count rises, so one popular institution doesn't get suggested for everything.
  4. **Profile-completeness nudge** (5 points) — a small bonus for having filled in any expertise/department/location data at all, so a blank profile doesn't accidentally tie with a filled-in one.
  - **The critical detail: signals 2-4 only apply if signal 1 found at least one real keyword overlap.** This is called "the gate" in the code comments. It was added after a bug was found during manual testing: Jharkhand's 24 districts are geographically small and close together, so almost *any* challenge/institution pair falls into at least the "reasonably close" proximity tier — meaning proximity (up to 25) + zero caseload (15) + profile bonus (5) could total 45 points, comfortably over the 35-point "good fit" badge threshold, for a challenge with **zero actual subject-matter relevance** to the institution (e.g. an Education-domain report showing up as "Good fit" for a Civil Engineering college purely because both happen to be in the same state and the college wasn't busy). Without the gate, this made the "Suggested for you" feature nearly meaningless — of 51 real+seeded open challenges tested, 34 were incorrectly flagged as suggested before the fix, versus 12 (all with genuine, inspectable keyword-overlap reasons) after it. The fix: when there is no keyword overlap at all, proximity and caseload still contribute *something* (so the admin's full ranked list — which shows every institution, not just badge-worthy ones — still has a sensible ordering even among poor matches), but their combined maximum in that branch is capped at 18 points, safely under the 35-point badge threshold, so a "good fit" or "strong fit" badge can never appear without at least one real keyword match behind it.
  - Missing/empty profile fields never subtract points — an institution that hasn't filled in `expertise` just doesn't earn signal 1 or 4, it isn't penalized below a filled-in competitor.

### Where this shows up in the app, and exactly how each surface behaves

All three of these call the AI functions above and fall back to `matching.ts` if the AI call hasn't resolved yet or has failed. None of them cache results across a page navigation — switching from the dashboard to the Challenges page re-triggers a fresh AI call rather than reusing the dashboard's result, since there is no shared client-side cache/store for this feature (a deliberate simplicity choice, not an oversight — Groq's free tier has enough headroom for a hackathon demo's traffic).

1. **`client/src/pages/InstituteChallenges.tsx`** (route `/institute/challenges`) — this is the institution's main challenge browser. Below the existing assignment queue, there are two pill-shaped tabs: **"All challenges"** (every open challenge, chronological, no AI call involved at all) and **"Suggested for you"** (only challenges the selected institution scored ≥35 on, sorted best-first). The AI call (`rankChallengesForInstitution`) fires **lazily** — only the first time the user actually clicks into the "Suggested for you" tab for a given institution, not on page load — specifically to avoid spending Groq quota on a tab the user might never open. Once clicked, a status line above the grid shows one of: a spinner + "Groq AI is analyzing N open challenges…" (call in flight, meanwhile the grid already shows the fallback-sorted results so there's never a blank screen); a `BrainCircuit` icon + "AI-powered matches for [institution] — ranked by academic fit, not just keywords" (call succeeded); or a muted "AI ranking is unavailable right now — showing an offline estimate for [institution] instead" (call failed), each state accompanied by a "Run AI match" / "Re-run AI match" button so the user can retry by hand (useful right after a transient failure, or just to demo the feature live). The URL supports `?tab=suggested` as a deep link, so other pages (see below) can link straight into this view. Every card in both tabs is a single large click target (not a small "View" link) that navigates to the public `/challenges/:id` page; the fit badge and the "Enroll" button inside the card both stop the click from also triggering that card-level navigation. Clicking a fit badge expands a short list of the model's (or fallback's) `reasons`, labeled "AI analysis" or "Offline estimate" so the source is unambiguous even at the level of a single card (since AI and fallback results can be mixed within one grid if the model's response happened to omit an entry for one specific challenge).
2. **`client/src/pages/InstituteDashboard.tsx`** (route `/institute/dashboard`, the institution's landing page after login) — a "Suggested for you" band sits between the summary stat cards and the "My assignments" table, showing only the **top 3** matches (score ≥35) as clickable cards, each also going straight to `/challenges/:id`. Unlike the Challenges page, this call fires **on page load** rather than waiting for a click — the dashboard is a short summary view where showing the best 3 matches immediately is the point, and 3 items is cheap. While the call is in flight and no fallback matches exist yet (rare, but possible on a very fresh profile), three pulsing gray skeleton boxes show in place of cards. A "View all suggested" link goes to `/institute/challenges?tab=suggested` — the deep link mentioned above. If the institution's profile has no `departments`/`expertise` filled in at all, this whole section is replaced by a single dashed prompt card ("Add your departments and expertise… to unlock personalized challenge matches here") linking to `/institute/profile`, rather than attempting to call AI on an empty profile and showing a meaningless result.
3. **`client/src/pages/AdminChallengeDetail.tsx`** (route `/admin/challenges/:id`) — the admin's single-challenge review screen. A "Suggested institutions" panel (top 3, score ≥35) sits above the existing manual assignment form, firing `rankInstitutionsForChallenge` on page load (same reasoning as the dashboard — a single challenge's worth of institutions is a cheap, worthwhile call to make immediately). Same status-line pattern as above, just in a smaller compact panel with a small icon-only "AI" refresh button instead of a full-width one. Clicking a suggested institution **only pre-fills the existing dropdown** in the assignment form below — it does not submit anything by itself. The dropdown's own option list is also sorted by score and annotated with the percentage (`"BIT Mesra — 82% fit"`). Nothing about the actual assignment action (`assignChallenge()`) changed — the admin still explicitly picks an institution and clicks "Assign challenge"; this feature is advisory-only, exactly as the original design spec below insisted it should be.

### Request lifecycle details worth knowing before touching this code

- **Lazy vs. eager triggering, and why:** the Challenges page's "Suggested" tab waits for a click; the dashboard and admin panel fire on mount. This isn't an inconsistency — it's a quota-conservation judgment call. The dashboard/admin calls are each small (top-3 or single-challenge scope) and central to what those pages are *for*; the Challenges page's call covers the institution's entire open-challenge list and the "All challenges" tab (the default view) doesn't need it at all, so firing it unconditionally on page load would waste a call on every visit that never even looks at "Suggested."
- **Request keys and stale-response guarding:** each of the three call sites tracks an in-flight "request key" (a string like `${institutionId}:${challengeCount}`) in a `useRef`. If the user switches institutions (or the challenge list changes size) while a call is still in flight, a new call starts with a new key; when the *old* call eventually resolves, its response is compared against the *current* ref value and discarded if they don't match. Without this, a slow, superseded response could overwrite newer, correct state — a classic race condition that's easy to introduce and easy to miss in manual testing (it doesn't show up unless you switch context mid-request).
- **No retry backoff, no queuing.** The "Re-run AI match" button just calls the same function again immediately. If Groq is still rate-limited, the user gets the same error again (and can see that in the same "AI ranking is unavailable" state). This is intentional simplicity for a hackathon-scale app, not a production rate-limiter.

### How this was verified (not just typechecked)

Both the AI path and the fallback path were exercised against real, live services — not mocked — using a throwaway Firebase Auth institution account and two synthetic challenges (one deliberately well-matched — a groundwater-contamination report near Ranchi, scored against an institution whose `expertise` included "water treatment, groundwater management, civil engineering" — and one deliberately unrelated — a street-lighting report), created via a one-off `firebase-admin` script and driven through the real dev server with Playwright (logging in through the actual `/login` form, not stubbing auth). Specifically confirmed:

- A real network request to `api.groq.com` fires when the Suggested tab is opened (checked via Playwright's request/response hooks, not assumed from the UI alone).
- The model's actual returned JSON reasons about domain mismatch correctly and without prompting for this specific case — in one real response, it scored the street-lighting report 15% ("Street lighting is an electrical infrastructure issue, not a core competency of Civil Engineering or Environmental Science departments") and an unrelated internet-connectivity report 10% ("an IT/telecom issue, outside the core civil/environmental scope"), in the same response that scored the genuine groundwater match 95%.
- The fallback path works under a **real** failure, not a simulated one: enough repeated test calls during this verification tripped Groq's actual free-tier rate limit (`429`, "Rate limit reached... on tokens per minute (TPM): Limit 8000"), and all three surfaces (Challenges tab, dashboard, admin panel) correctly caught it and displayed their "offline estimate" fallback state rather than erroring or hanging.
- All throwaway Firebase Auth users and Firestore documents created for this testing were deleted immediately afterward via a matching cleanup script — nothing from this verification was left in the live `samadhan-sih` project.

### What is *not* built (fast-follow ideas, not gaps in what was asked for)

- No caching of AI results across page navigations or across users — every page load that needs a ranking makes its own fresh call. Fine at hackathon-demo traffic levels; would need addressing (e.g. a short-TTL cache keyed by institution+challenge-set) before any real production traffic.
- No rate-limit backoff/retry queue — see above.
- `organizations.expertise`/`departments`/`priorityDomains` remain free text, not a structured tag vocabulary (this was already called out as a fast-follow in the original design spec below, and remains one — the AI approach actually reduces the urgency of this, since a free-text-savvy model handles messy input better than the keyword-overlap fallback does).

## Original design spec (historical — read the section above for what's actually built)

## Real-world problem

The SIH 2026 problem statement (ID 26043) does not just ask for a citizen-reporting portal. Its "Expected Solution" section explicitly calls for:

> "An AI-enabled problem management module capable of automatically categorizing, prioritizing, deduplication, **and routing validated challenges to appropriate universities based on subject expertise and institutional capabilities**."

and the background section calls for:

> "Routing validated problem statements to appropriate universities based on their **academic disciplines, research expertise, innovation centres, incubation facilities, and faculty specialization**."

This is not an optional nice-to-have — it is named, specifically, in the official problem statement Samadhan is being built for. **As verified against the actual codebase in this session, Samadhan does not do this today.** `client/src/lib/db.ts`'s `assignChallenge()` (admin manually picks one verified institution) and `enrollChallenge()` (an institution self-enrolls for any open challenge it chooses) are the only two paths a challenge reaches an institution. Neither looks at what the institution is actually good at. An institution can self-enroll for a challenge completely outside its expertise (a pure-arts college enrolling for a groundwater-engineering challenge), and admin assignment is a human manually eyeballing a list with no decision support.

## Research/evidence behind the problem

- `research/22.pdf` §33.1 (verified directly from the PDF in this session): NITI Aayog's *Establishing New Universities in India* analysis found **Ranchi has 18 universities while several of Jharkhand's Aspirational Districts have zero**. Academic capacity is not just "insufficient" — it is geographically lopsided. A citizen's own district frequently has no institution capable of taking their problem at all.
- `docs/RESEARCH_ANALYSIS.md` §1.2 draws the same conclusion independently: "Jharkhand's Actual Problem Is Routing, Not Data."
- The `organizations` table (`drizzle/schema.ts:38-39, 83-85`) already has **`departments` and `expertise` free-text fields**, collected at institution onboarding — verified directly in the schema file during this session. They are stored but, as of this session, **read by nothing** in `db.ts`, `enrollChallenge()`, or `assignChallenge()`. The data the matching engine needs already exists in the database; it is simply never used for a match.

## Who is affected

- **Citizens in Aspirational Districts with zero local universities** (per the NITI Aayog finding above) — their reports currently rely entirely on an institution somewhere else in the state noticing and choosing to self-enroll, or an admin manually noticing the gap.
- **Admins**, who currently have no decision support when using `assignChallenge()` — they either already know every institution's specialization from memory, or they're guessing.
- **Institutions themselves**, who currently browse an undifferentiated list of "Available challenges" (`InstituteChallenges.tsx`) with no signal for which ones actually fit their department/faculty strengths, wasting review time and risking a mismatched self-enrollment that stalls later (a civil-engineering problem picked up by a college with no civil faculty).

## Why existing systems fail

CPGRAMS and MyGov route grievances to a *department*, not to a specific institution with matching subject-matter capability — there is no equivalent concept in a generic government grievance system, because they don't involve universities at all. UMANG aggregates services; it doesn't match a problem to a solver. FixMyStreet routes by category to whichever single council owns that road — a 1:1 geographic mapping, not a many-to-many expertise match. None of the reference systems researched actually solve "which of N eligible organizations is the best fit for this specific problem," because none of them have Samadhan's citizen→university structure at all.

## Proposed Samadhan solution

A **match-score engine**, computed entirely client-side (no new backend — consistent with the rest of Samadhan's architecture) from data that already exists in Firestore:

1. **Institution profile signal** — the existing `organizations.departments` / `organizations.expertise` free-text fields, tokenized into a keyword set at read time (no schema change needed to start; a structured multi-select tag field is a fast-follow improvement, see below).
2. **Challenge domain signal** — the existing `challenges.domain` field (`Water | Education | Health | Agriculture | Infrastructure | Livelihoods`, per `SubmitChallenge.tsx`'s dropdown) plus the free-text `description`.
3. **Geographic proximity signal** — `challenge.district` vs. the institution's registered district/location, using the same `JHARKHAND_DISTRICTS` centroid data `InteractiveMap.tsx`/`AdminReports.tsx` already use for GIS, so a nearer institution scores higher than a distant one, all else equal.
4. **Capacity/load signal** — how many `assignments`/`projects` an institution already has active (from the same `assignments` collection the self-enrollment flow already reads), so an overloaded institution scores lower and a match doesn't pile every good-fit challenge onto one popular college.

These four signals combine into a **match score per (challenge, verified institution) pair**, surfaced two ways, neither of which removes human judgment:

- **On `InstituteChallenges.tsx`'s "Available challenges" list**, a per-card "Fit for your institution" badge/percentage, sorted by fit instead of chronological order — so an institution's own faculty spend their limited attention on the challenges most likely to be a good match, without losing the ability to self-enroll for anything else.
- **On `AdminChallengeReview.tsx`-equivalent admin assignment screens**, a ranked list of "Suggested institutions" for a given unassigned challenge, replacing the current blind manual pick — admin still clicks the final "Assign" button, this only orders and annotates the choice.

## How it works (realistic example)

A citizen in Latehar (a NITI Aayog Aspirational District with no local university, per the verified research finding above) reports a groundwater-contamination problem, domain `Water`. Today: the report sits until some institution happens to notice it in the open list, or an admin manually remembers which of the state's ~9 universities has a water/civil/environmental engineering department. With USP-08: the moment the challenge is validated, the engine scores every verified institution — BIT Mesra's civil engineering department and expertise keywords ("water", "environmental") score high even though BIT Mesra is in Ranchi, not Latehar, because domain-fit outweighs raw distance once a threshold is met; a nearby college with an unrelated speciality (say, a purely commerce-focused institution) scores low despite being geographically closer. The admin's assignment screen now shows BIT Mesra at the top with a "Water · Civil/Environmental Engineering match" tag instead of an alphabetical list, and BIT Mesra's own "Available challenges" view shows this Latehar report near the top of its own feed too.

## What makes this genuinely different

This is not "yet another AI classification feature" layered on for its own sake — Samadhan already has AI classification (Groq Vision auto-categorize, per `docs/CLAUDE.md`'s "AI Auto-Categorize" section, verified implemented in this session) and duplicate detection. USP-08 solves a **different, more specific problem named explicitly in the actual SIH problem statement**: not "what domain is this" but "which specific verified organization, out of all the ones on the platform, is the right one to solve it." No existing civic-tech reference platform researched (CPGRAMS, MyGov, UMANG, FixMyStreet, Ushahidi) has an equivalent many-to-many expertise-matching mechanism, because none of them route to specialized third-party solver organizations at all — they route to a single fixed government department. Samadhan's own current implementation (self-enrollment + manual admin assignment, both verified against the live code in this session) also does not do this — it's a real, current gap, not a renamed existing feature.

## Impact

- Directly closes a requirement stated in the problem statement itself — the single most judge-defensible reason to build this, since a judge reading the problem statement will notice the routing requirement immediately if it isn't there.
- Turns the already-collected-but-unused `organizations.departments`/`expertise` fields into an actual product feature instead of dead data.
- Specifically helps citizens in the Aspirational Districts the research flagged as having zero local university capacity, by surfacing the right *distant* institution instead of relying on chance discovery.

## Why this qualifies as a USP

Real problem (explicit PS requirement, unaddressed as of this session) → specific mechanism (four-signal match score over already-collected data, computed client-side, no new backend) → measurable impact (faster time-to-enrollment for well-matched challenges, fewer mismatched self-enrollments that stall later) → clear differentiation (no reference system researched routes many-to-many by expertise; Samadhan's own current implementation doesn't either).

## Technical approach

- New pure function module `client/src/lib/matching.ts` (no Firestore calls of its own — takes already-fetched `challenges`/`organizations`/`assignments` arrays, mirroring the existing pattern in `client/src/lib/analytics.ts` for USP-05): `scoreInstitutionsForChallenge(challenge, organizations, assignments): { organizationId, score, reasons }[]`.
- Domain/keyword matching starts as simple token overlap between `challenge.domain`/`description` and `organization.departments`/`expertise` (same class of heuristic already used and shipped in `client/src/lib/bhasha.ts`'s `DOMAIN_KEYWORDS` and `duplicateCheck.ts`'s word-overlap similarity — consistent with the project's existing "naive heuristic, no paid AI call" pattern rather than introducing a new dependency).
- Geographic distance reuses the district centroid table already present for `InteractiveMap`/`AdminReports` (`JHARKHAND_DISTRICTS`) — no new geodata needed.
- No `firestore.rules` change required — this only reads already-world-readable `organizations`/`challenges`/`assignments` collections; it doesn't need to write anything new (the ranked list is a client-side computed view, not a stored field), so the two-step "client deploy + rules deploy" split isn't triggered.
- Fast-follow, not required for v1: replace `organizations.expertise` free text with a structured multi-select tag field (chosen from a fixed vocabulary at institution onboarding/profile edit) for a more reliable match than free-text token overlap — this is a schema-compatible additive change (`drizzle/schema.ts` is schemaless in Firestore already; old free-text-only org records simply have no tags and fall back to the free-text heuristic).

## Integration with the existing system

- Renders on `InstituteChallenges.tsx` (existing "Available challenges" section, USP self-enrollment feature) as a sort key and badge — no new route.
- Renders on the existing admin challenge-assignment surface as a ranked "Suggested institutions" panel above the current plain organization picker.
- Does not change `enrollChallenge()`/`assignChallenge()` themselves — self-enrollment stays open to any verified institution for any challenge (institutions can still legitimately want to pick up something outside their core department), and admin still makes the final call. The engine is a **ranking and surfacing layer**, not a gatekeeper — this deliberately avoids the failure mode of an opaque auto-router silently blocking a legitimate cross-disciplinary match.

## Accessibility/inclusivity considerations

Purely an institution/admin-side feature — no citizen-facing UI, so no new literacy/language/connectivity burden on the reporting citizen. The badge/ranking text should still go through the existing i18n/live-translate layer (`AutoTranslate.tsx`) for institution users who prefer Hindi.

## Government adoption considerations

Directly supports the research-cited Jharkhand Startup Policy 2021 / IIT Madras–Jharkhand University of Technology partnership pattern (`research/22.pdf` §33.2, verified) of connecting existing institutional capability to real problems rather than creating new institutions — the pitch to a government stakeholder is "we route to your existing university network intelligently," not "we require new infrastructure."

## Scalability considerations

Purely client-side computation over already-fetched collections scales the same way the rest of Samadhan's read-heavy client architecture does — no new server, no new Firestore reads beyond what `InstituteChallenges.tsx`/admin pages already fetch. At larger institution counts (hundreds instead of the current handful of seeded/onboarded orgs), the O(challenges × organizations) score computation is still cheap in-browser for realistic Jharkhand-scale numbers (9 universities + 246 colleges per the research's own verified count), but would need a cap/pagination if the platform scaled to multi-state.

## Abuse/failure cases and mitigation

- **Failure case: free-text `expertise` field is empty or vague for an institution that never filled it in carefully.** Mitigation: score falls back to domain-only + geographic proximity; a "no expertise data" institution isn't excluded, just unranked/lower-confidence, and its own profile page can nudge it to fill in `expertise` with a "complete your profile to appear in better matches" prompt.
- **Failure case: an institution "games" its `expertise` field with broad/irrelevant keywords to rank for everything and monopolize challenges.** Mitigation: the capacity/load signal already down-weights institutions with many active assignments, which naturally throttles a single institution from absorbing every challenge regardless of keyword-stuffing; this is a ranking signal an admin sees, not an automatic gate, so an admin noticing a suspicious pattern can still assign elsewhere.
- **Failure case: matching engine has systematic geographic bias (always prefers Ranchi-based institutions because they're best-resourced and best-profiled).** Mitigation: this is the exact problem the research flagged (18 vs 0 universities) — the design deliberately weights domain/keyword fit above raw distance past a reasonable radius, specifically so a well-matched distant institution can still outrank a poorly-matched nearby one; this tradeoff should be explicitly stated to judges as a design decision, not hidden.

## Likely SIH judge questions and answers

**Q: "Isn't this just your existing AI auto-categorization feature renamed?"**
A: No — auto-categorization (Groq Vision) answers "what domain is this challenge," which already exists and is unrelated. USP-08 answers a different question named explicitly in the problem statement: "which specific verified organization should solve it." They operate on different data (challenge photo vs. institution profile) and solve different steps of the pipeline.

**Q: "What if the AI recommends the wrong institution?"**
A: It doesn't decide — it ranks and suggests. `assignChallenge()` still requires an admin's explicit click, and `enrollChallenge()` remains open to any verified institution regardless of its rank. This is deliberately advisory, not automated, exactly because a wrong automated routing decision (e.g., for a sensitive or ambiguous problem) could be worse than the current manual process.

**Q: "How do you know your matching actually works, given you don't have real usage data yet?"**
A: We don't claim a validated accuracy number — that would be fabricated. The honest claim is: the four signals used (domain keyword overlap, geographic proximity, institution-stated expertise, current capacity) are the same signals the problem statement itself names ("academic disciplines, research expertise... faculty specialization"), and the mechanism is transparent/inspectable (each suggestion shows its reasons) rather than a black box, so an admin can sanity-check and override any suggestion trivially.
